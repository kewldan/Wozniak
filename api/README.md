# HTTP API

[`openapi.yaml`](openapi.yaml) is the contract between `jobrun`, the server
and the web panel. Change it first, in its own pull request, and only then
change the code on either side.

All paths start with `/api/v1`. nginx forwards `/api/` to the server
unchanged, so the same paths work through the Compose stack
(`http://localhost:8080`) and against the server directly.

| Method | Path | Who calls it | Purpose |
|--------|------|--------------|---------|
| `POST` | `/api/v1/events` | jobrun | Report a run start or finish |
| `GET`  | `/api/v1/jobs` | panel | All jobs with state and latest run |
| `GET`  | `/api/v1/jobs/{job_id}` | panel | One job |
| `GET`  | `/api/v1/jobs/{job_id}/runs` | panel | Run history, newest first, paginated |
| `GET`  | `/api/v1/runs/{run_id}` | panel | Run details with both events |
| `GET`  | `/api/v1/health` | Docker, monitoring | Server and database are up |

Lint the spec after every change:

```bash
make api-lint
```

## Events

A run produces two events with the same `run_id`: `start` right before the
command starts and `finish` after it exits.

| Field | start | finish | Meaning |
|-------|-------|--------|---------|
| `type` | `start` | `finish` | Event type |
| `job_id` | required | required | Job ID from the server configuration |
| `run_id` | required | required | UUID generated by jobrun (UUIDv7 recommended) |
| `occurred_at` | required | required | Wrapper clock, RFC 3339; display only |
| `host` | optional | optional | Hostname of the machine |
| `exit_code` | — | required | 0–255; `128+N` on signal N, `127` not found, `126` not executable |
| `duration_ms` | — | required | Run time measured by jobrun with a monotonic clock |
| `message` | optional | optional | Short note, up to 1024 characters |

Deadlines are computed from the server's clock (`received_at`), never from
`occurred_at`. If the command cannot be started at all, jobrun still sends a
`finish` with `exit_code` 127 or 126 and the error in `message`.

### Start

```bash
curl -i http://localhost:8080/api/v1/events \
  -H "Authorization: Bearer $WOZNIAK_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "type": "start",
    "job_id": "nightly-backup",
    "run_id": "019aa1f0-7c3e-7d2a-9b1e-3f5c2a8d4e61",
    "occurred_at": "2026-11-20T03:00:00.412Z",
    "host": "vm-01"
  }'
```

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"run_id":"019aa1f0-7c3e-7d2a-9b1e-3f5c2a8d4e61","type":"start","received_at":"2026-11-20T03:00:00.530Z","duplicate":false}
```

### Finish

```bash
curl -i http://localhost:8080/api/v1/events \
  -H "Authorization: Bearer $WOZNIAK_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "type": "finish",
    "job_id": "nightly-backup",
    "run_id": "019aa1f0-7c3e-7d2a-9b1e-3f5c2a8d4e61",
    "occurred_at": "2026-11-20T03:00:05.020Z",
    "host": "vm-01",
    "exit_code": 2,
    "duration_ms": 4608,
    "message": "pg_dump: connection to server failed"
  }'
```

### Validation error

```http
HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{
  "title": "Validation failed",
  "status": 400,
  "code": "validation_failed",
  "errors": [{"field": "exit_code", "message": "required for finish events"}]
}
```

## Delivery rules for jobrun

- **Idempotency.** The server stores one event per (`run_id`, `type`). A
  repeat returns `200` with `"duplicate": true` and keeps the first copy, so
  retrying the same body is always safe.
- **Any order.** A `finish` without a `start` is accepted and creates the
  run.
- **Retries.** Retry on network errors, timeouts, `500` and `503` with
  backoff, but never delay or change the command's exit code. Do not retry
  other `4xx`: they mean a configuration error (bad token, unknown job,
  invalid body), so log the problem and move on.
- **Size.** Bodies are limited to 16 KiB by the server and 64 KiB by nginx.

| Status | Code | Retry | Meaning |
|--------|------|-------|---------|
| 201 | — | — | Stored |
| 200 | — | — | Duplicate, already stored |
| 400 | `invalid_json`, `validation_failed` | no | Bad body |
| 401 | `unauthorized` | no | Missing or unknown token |
| 403 | `forbidden` | no | Token not allowed for this job |
| 409 | `run_job_mismatch` | no | `run_id` belongs to another job |
| 413 | `payload_too_large` | no | Body over 16 KiB |
| 415 | `unsupported_media_type` | no | Not `application/json` |
| 422 | `unknown_job` | no | Job is not configured on the server |
| 500 | `internal` | yes | Server error |
| 503 | `unavailable` | yes | Database unreachable |

## Read API for the panel

- `GET /api/v1/jobs` returns every job sorted by `id`, its `state`, deadline
  settings, `next_start_due_at`, `last_run` and the current `server_time`.
  The list is not paginated.
- `GET /api/v1/jobs/{job_id}/runs?limit=20&cursor=…` pages through history.
  Pass `next_cursor` from the previous page; it is `null` on the last one.
  `limit` is 1–100, default 20.
- `GET /api/v1/runs/{run_id}` adds both events with wrapper and server times,
  hostname and message.
- `duration_ms` of a run is shown only when both events were received. The
  value from a finish without a start is still available as
  `finish.reported_duration_ms` in the run details.

Read endpoints are open for now; panel sign-in is decided in M3.

### States

| `JobState` | Meaning |
|------------|---------|
| `pending` | Monitoring started, no runs yet, first start not due |
| `running` | Latest run started, finish not due yet |
| `succeeded` | Latest run finished with exit code 0 |
| `failed` | Latest run finished with a non-zero exit code |
| `finish_overdue` | No finish confirmation in time |
| `start_overdue` | No expected start |

`RunStatus` is `running`, `succeeded`, `failed` or `finish_overdue`. A run
whose finish came after `finish_due_at` keeps its real result and gets
`"late": true`. The rules that derive these values are in the state model
(issue #10).

TypeScript types for the panel can be generated from the spec:

```bash
bunx openapi-typescript ../api/openapi.yaml -o src/lib/api-types.ts
```
